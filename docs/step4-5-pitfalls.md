# Step 4~5 구현 시 자주 막히는 지점

## 1. RuleNode에서 자주 나는 문제

### 1-1. 포트 이름 불일치

명세 포트 이름은 정확히 맞춰야 한다.

- 입력: `"in"`
- 출력: `"match"`, `"mismatch"`

여기서 `"out"` 같은 이름을 습관적으로 쓰면 테스트에서 바로 깨진다.

### 1-2. null-safe 처리 누락

예:

```java
Double temp = message.get("temperature");
return temp > 30.0;
```

이렇게 쓰면 `temperature`가 없는 메시지에서 `NullPointerException`이 난다.

반드시 이런 식이어야 한다.

```java
Double temp = message.get("temperature");
return temp != null && temp > 30.0;
```

### 1-3. match/mismatch에 같은 메시지를 그대로 보내는지 확인

RuleNode는 보통 메시지를 변형하지 않고 분기만 한다.

즉:

- `send("match", message)`
- `send("mismatch", message)`

기존 메시지를 그대로 보내는 게 맞다.

## 2. RuleExpression에서 자주 막히는 문제

### 2-1. 숫자와 문자열 비교를 섞어서 처리함

예:

- `"temperature > 30.0"` -> 숫자 비교
- `"status == ON"` -> 문자열 비교

비교 타입이 섞이면 평가 로직이 쉽게 꼬인다.

처음에는 단순하게 다음 규칙으로 처리하는 게 낫다.

- 값이 숫자로 파싱되면 `Double`
- 아니면 `String`

### 2-2. 잘못된 표현식 예외 처리 누락

예:

- `"temperature"`
- `"temperature >"`
- `"temperature >< 30"`

이런 표현식은 `parse()` 단계에서 바로 예외를 던져야 한다.

애매하게 넘어가면 테스트도 지저분해지고 런타임 오류가 커진다.

### 2-3. 공백 기준 split만 믿고 확장하려고 함

현재 과제 수준에서는:

```java
expression.trim().split("\\s+")
```

정도로 충분하다.

괄호, 따옴표, AND/OR, 중첩 표현식까지 한 번에 넣으려 하면 바로 복잡도가 튄다.

## 3. CompositeRuleNode에서 흔한 실수

### 3-1. AND/OR 기본 동작을 정의하지 않음

빈 조건일 때 기본값이 있어야 한다.

- AND: `match`
- OR: `mismatch`

이걸 명시하지 않으면 테스트에서 바로 흔들린다.

### 3-2. 단일 노드에 너무 많은 책임을 넣음

조건이 복잡하다고 해서 `CompositeRuleNode` 하나에 모든 의미를 넣기 시작하면 가독성이 급격히 떨어진다.

현재 프로젝트에서는:

- 단순 분기 -> `RuleNode`
- 여러 조건 묶기 -> `CompositeRuleNode`

정도로 역할을 나누는 게 맞다.

## 4. TimeWindowRuleNode에서 자주 터지는 문제

### 4-1. 이벤트 제거 순서를 잘못 잡음

순서는 이게 맞다.

1. 조건 평가
2. 만족 시 현재 시간 추가
3. 오래된 이벤트 제거
4. threshold 비교

이 순서가 틀리면 카운트가 1씩 어긋난다.

### 4-2. 메시지 시간과 처리 시간을 혼동함

현재 과제에서 가장 단순한 기준은 **노드 처리 시각**이다.

즉:

```java
long now = System.currentTimeMillis();
```

를 기준으로 큐를 관리하면 된다.

나중에 네트워크 지연을 엄밀히 다루려면 메시지에 포함된 event timestamp를 써야 한다.

### 4-3. 한 번 alert가 나간 뒤 계속 alert가 나가는 문제

이건 설계 선택이다.

현재 과제 명세만 보면 threshold 이상이면 계속 `alert`로 보내도 틀리진 않는다.

다만 실제 운영에서는 중복 알림 제어가 필요할 수 있다.

## 5. MQTT + Rule + MODBUS 통합에서 흔한 문제

### 5-1. MQTT Broker가 안 떠 있음

이건 가장 먼저 확인해야 한다.

- `localhost:1883`
- Mosquitto 실행 여부

Broker가 안 떠 있으면 RuleNode 이전에 MQTT 노드부터 실패한다.

### 5-2. MQTT subscriber 재구독 누락

자동 재연결만 켜 두고 재구독을 안 하면, Broker 재시작 후 메시지를 못 받는 상태가 생긴다.

현재 구조에서는 `connectComplete()`에서 재구독하는 방식이 안전하다.

### 5-3. MODBUS writer가 입력 메시지 값을 그대로 쓰는 문제

Step 4 플로우에서 “조건 만족 시 팬 가동 명령 1 쓰기” 같은 경우는 입력 메시지의 온도값을 그대로 쓰면 안 된다.

이 경우는:

- `fixedValue`
- 또는 `TransformNode`

둘 중 하나가 필요하다.

현재 코드베이스에서는 `fixedValue` 방식이 가장 단순하다.

### 5-4. Rule match 경로를 두 갈래로 못 보냄

Step 4-4는 보통 `match`가 두 군데로 가야 한다.

- `MqttPublisherNode`
- `ModbusWriterNode`

즉 출력 포트가 다중 연결을 제대로 지원하는지 먼저 확인해야 한다.

## 6. 통합 테스트에서 자주 나는 문제

### 6-1. 외부 시스템 테스트와 단위 테스트를 섞음

MQTT Broker가 필요한 테스트는 `@Tag("integration")`로 분리해야 한다.

그렇지 않으면 `mvn test` 할 때 환경 따라 계속 흔들린다.

### 6-2. 포트 충돌

테스트에서 `1883`, `5020` 같은 포트를 고정으로 쓰면 병렬 실행이나 잔여 프로세스 때문에 충돌할 수 있다.

MODBUS 쪽은 가급적 테스트용 동적 포트를 쓰는 게 낫다.

MQTT는 Broker 포트가 고정인 경우가 많으니 테스트 전 실행 상태를 명시적으로 가정해야 한다.

### 6-3. 소켓 종료 후 예외 로그가 과하게 남음

예:

- `EOFException`
- `SocketException: Socket closed`

클라이언트 정상 종료 흐름까지 예외로 찍히면 테스트는 통과해도 품질이 떨어진다.

정상 종료와 진짜 오류를 구분해서 처리해야 한다.

## 7. 성능 측정에서 자주 틀리는 점

### 7-1. throughput과 latency를 한 숫자로 뭉개서 봄

둘은 다르다.

- throughput: 초당 몇 건 처리했는가
- latency: 메시지 하나가 끝까지 가는 데 얼마나 걸렸는가

둘 다 따로 봐야 한다.

### 7-2. warm-up 없이 바로 측정

JVM은 초반 몇 번 실행이 불안정할 수 있다.

가능하면:

1. warm-up
2. 실제 측정

으로 나누는 게 낫다.

### 7-3. 큐 적체를 안 보고 throughput만 봄

메시지를 많이 집어넣는다고 처리량이 진짜 높은 게 아니다.

뒤쪽 큐가 계속 쌓이면:

- latency 증가
- 메모리 증가
- 결국 지연 폭증

즉 queue backlog도 같이 봐야 한다.

## 8. 현재 코드베이스 기준 주의할 점

### 8-1. MQTT는 이미 한 번 라이브러리 경로 문제를 밟았다

우리가 실제로 겪은 문제:

- `subscribe(..., listener)` 경로에서 `StackOverflowError`

그래서 현재는 `MqttAsyncClient + MemoryPersistence`로 정리돼 있다.

즉 Step 4~5에서 MQTT 코드를 손댈 때는 이 선택을 다시 깨지 않게 주의해야 한다.

### 8-2. MODBUS 통합 테스트는 로컬 소켓 바인드가 필요하다

로컬 환경에서는 문제 없지만, 제한된 실행 환경에서는 `ServerSocket` 바인드가 막힐 수 있다.

즉 CI나 샌드박스 환경에서는 권한/네트워크 제한을 먼저 확인해야 한다.

## 9. 추천 대응 방식

Step 4~5에서 막히면 아래 순서로 확인하면 된다.

1. 포트 이름이 명세와 일치하는가
2. null-safe 처리가 되어 있는가
3. 외부 시스템 의존 테스트를 분리했는가
4. MQTT Broker / MODBUS 시뮬레이터가 실제로 떠 있는가
5. match/mismatch 또는 alert/pass 분기가 기대대로 연결됐는가
6. 고정값 쓰기인지, 입력값 쓰기인지 설계가 맞는가
7. 로그에 찍힌 예외가 진짜 실패인지 정상 종료인지 구분했는가

## 10. 강의자료에서 일부러 부딪히게 둘 수 있는 함정

모든 항목이 의도된 것이라고 단정할 수는 없지만, 학습용 과제에서는 아래 같은 모순이나 불완전함을 일부러 남겨 둘 수 있다. 이런 걸 직접 발견하고 정리하는 것 자체가 학습 포인트가 된다.

### 10-1. 이름은 엔진인데 실제 엔진 역할은 안 하는 구조

초기 `FlowEngine`은 등록/상태 관리만 하고 실제 worker thread는 runner가 직접 만들고 있었다.

겉으로는 엔진처럼 보이지만 실제 메시지 실행은 밖에서 하고 있었기 때문에, “이 클래스가 정말 엔진 역할을 하는가?”를 스스로 따져보게 만드는 지점이었다.

### 10-2. 숨겨진 메시지 규약

`MergeNode`는 `_inputPort` 키가 있어야 동작했지만, 그 키를 주입하는 코드는 처음엔 없었다.

이건 다음을 배우게 한다.

- 노드 간 암묵적 규약은 위험하다
- 포트 메타데이터가 필요하면 어디서 주입할지 명확해야 한다
- 테스트만 통과하고 실제 연결 경로는 깨질 수 있다

### 10-3. 라이브러리 사용 예시가 항상 안전한 건 아니다

MQTT에서는 `subscribe(..., listener)` 같은 예시가 교재나 문서에 있어도, 실제 라이브러리 버전/호출 경로에 따라 문제가 날 수 있다.

우리가 실제로 겪은 건:

- `subscribe(..., listener)` 경로에서 `StackOverflowError`
- 기본 file persistence 사용 시 `.lck`, `mqtt-*` 디렉토리 생성

이건 “문서 예시를 그대로 쓰는 것”과 “현재 환경에서 안정적으로 동작하는 것”은 다를 수 있다는 점을 보여준다.

### 10-4. 공통 부모가 비어 있는 상태로 남아 있을 수 있다

`SensorNode`가 비어 있었던 건 공통화가 덜 된 흔적이었고, 다음 질문을 던지게 만든다.

- 이 클래스는 정말 필요한가
- 공통 부모로 추출할 책임이 있는가
- 아니면 삭제하는 게 맞는가

즉 “추상화는 이름만 있다고 끝나는 게 아니다”를 배우게 하는 지점이다.

### 10-5. 호환용 API가 오히려 혼란을 만들 수 있다

`ModbusTcpClient`의 레거시 생성자/`connect(host, port)` 같은 API는 겉보기엔 편하지만, 실제로는 잘못된 사용 경로를 늘리고 설계를 흐릴 수 있다.

이런 흔적은 다음을 점검하게 한다.

- 이 API가 지금도 실제로 쓰이는가
- 남겨두는 비용이 이득보다 큰가
- 명세와 실제 구현이 어긋나지 않는가

### 10-6. archetype 기본 코드나 중복 설정도 학습 포인트다

`App.java`의 `Hello World`, `pom.xml`의 `release + source/target`, 예시 URL 같은 건 기능은 안 깨도 품질을 떨어뜨린다.

이건 “돌아가는 코드”와 “정리된 프로젝트”는 다르다는 점을 보여준다.

### 10-7. 순서에 의존하는 코드는 쉽게 깨진다

`flow.getConnections().get(0)` 같은 코드는 당장은 되지만 연결 순서가 바뀌면 바로 취약해진다.

이건 다음을 배우게 한다.

- 위치 기반 접근보다 ID 기반 접근이 안전하다
- 실행 구조가 커질수록 명시적 이름이 중요하다
- “지금 돌아간다”와 “나중에도 안 깨진다”는 다르다

### 10-8. 테스트가 다 통과해도 구조는 여전히 나쁠 수 있다

이 과제 전반에서 가장 중요한 함정은 이거다.

- 테스트 통과
- 기능 동작

이 두 가지가 곧 좋은 구조를 뜻하지는 않는다.

즉, 과제는 구현뿐 아니라 다음 질문까지 하게 만든다.

- 책임이 제대로 나뉘어 있는가
- 이름과 역할이 일치하는가
- 암묵적 규약이 숨어 있지 않은가
- 운영 중에도 버틸 구조인가

### 10-9. 강의자료 예제는 일부러 거칠게 남겨뒀을 수 있다

강의자료 예제는 학습 포인트를 드러내려고 최소 형태로 적혀 있는 경우가 있다.

예:

- `subscribe(..., listener)`처럼 실제 라이브러리 버그 경로를 밟을 수 있는 예제
- 파일 persistence 부산물이 생기는 기본 생성자 사용
- `System.out.println()` 중심의 빠른 데모 코드
- 오타가 섞인 클래스 이름이나, 최소 동작만 확인하는 네트워크 예제

이건 "코드에 일부러 버그를 넣어야 한다"는 뜻이 아니다.

의미는 이쪽에 가깝다.

- 학습자가 직접 문제를 발견하게 하려는 흔적일 수 있음
- 자료의 범위가 생산 코드까지 정리하는 수준은 아닐 수 있음

그래서 실제 제출 코드에서는:

- 동작 확인용 예제
- 제출용 구조 코드

를 구분해서 보는 게 맞다.
