# Step 4-1 ArrayList 기반 생산자-소비자 실험 보고서

## 1. 실험 목적
`ArrayList<String>`를 공유 버퍼로 사용하여 생산자-소비자 구조를 구현하고, 동시성 환경에서 어떤 문제가 발생하는지 직접 확인한다.

## 2. 실험 구성
공유 버퍼는 아래와 같이 `ArrayList<String>`로 선언하였다.

```java
ArrayList<String> buffer = new ArrayList<>();
```

스레드는 다음과 같이 구성하였다.

- 생산자 스레드
  0.1초 간격으로 `"메시지-0"`부터 `"메시지-99"`까지 버퍼에 추가
- 소비자 스레드
  `while` 루프 안에서 `buffer.isEmpty()`를 계속 검사
- 소비자 동작
  버퍼가 비어 있지 않으면 `buffer.remove(0)`으로 메시지를 꺼내 출력

## 3. 실행 중 관찰한 내용

### 3-1. 버퍼 접근이 안전하지 않았다
실행해보니 생산자와 소비자가 같은 `ArrayList`를 동시에 수정하는 구조였다. `ArrayList`는 스레드 안전하지 않기 때문에, 실행 타이밍에 따라 버퍼 상태가 예상과 다르게 바뀔 수 있었다.

특히 소비자는 먼저 `isEmpty()`를 확인한 뒤, 그 다음에 `remove(0)`을 수행한다. 그런데 이 두 동작 사이에 다른 스레드가 버퍼를 변경할 수 있으므로, 검사 시점과 실제 삭제 시점의 상태가 달라질 위험이 있었다.

이 때문에 경우에 따라 `IndexOutOfBoundsException` 같은 예외가 발생할 수 있고, 메시지 처리 결과도 신뢰하기 어렵다고 판단했다.

### 3-2. 메시지 유실 또는 중복 가능성이 있었다
공유 버퍼에 대한 접근이 동기화되지 않았기 때문에, 생산자와 소비자가 동시에 동작할 때 메시지가 정상적인 순서와 개수로 처리된다고 보장할 수 없었다.

실행 로그를 보면 대부분 정상처럼 보여도, 구조 자체가 경쟁 조건을 가지고 있어서 메시지 유실이나 중복 처리 가능성이 존재한다. 즉, "이번 실행에서 괜찮아 보였다"와 "항상 안전하다"는 전혀 다른 문제라는 점을 확인했다.

### 3-3. 소비자 스레드가 busy-waiting 상태였다
소비자 스레드는 계속 반복문을 돌며 버퍼 상태를 확인하였다.

- 버퍼가 비어 있어도 쉬지 않음
- 메시지가 없어도 CPU를 계속 사용

이 구조는 busy-waiting 문제에 해당한다. 실제로 생산자가 아직 메시지를 넣지 않았거나 이미 종료한 뒤에도 소비자는 계속 루프를 돌게 된다. 즉, 일이 없는데도 CPU를 낭비하는 비효율적인 방식이라는 점을 확인했다.

### 3-4. 생산 종료 후 소비자의 종료 시점을 알 수 없었다
생산자는 `"메시지-99"`까지 생성하면 종료할 수 있다. 하지만 소비자는 버퍼가 잠깐 비어 있는 상황과, 생산이 완전히 끝난 상황을 구분할 수 없다.

즉 현재 구조에서는 다음 문제가 생긴다.

- 버퍼가 잠깐 비어도 생산자가 다시 넣을 수 있음
- 버퍼가 비었고 생산자도 끝났는지 소비자는 알 수 없음
- 결과적으로 소비자가 언제 종료해야 하는지 판단할 수 없음

그래서 소비자는 무한 루프에 빠지기 쉽고, 프로그램 종료 제어도 어렵다는 점을 확인했다.

## 4. 문제 원인 분석

### 4-1. ArrayList는 동시성 버퍼로 적합하지 않음
`ArrayList`는 여러 스레드가 동시에 접근하는 상황을 안전하게 처리하지 않는다. 따라서 생산자-소비자처럼 공유 자원에 동시에 접근하는 구조에서는 적합하지 않다.

### 4-2. 검사와 실행이 분리되어 경쟁 조건이 발생함
소비자는 `isEmpty()`로 상태를 확인한 뒤 `remove(0)`을 수행한다. 이 두 동작이 하나로 묶여 있지 않기 때문에, 다른 스레드가 중간에 버퍼를 바꾸면 오류나 비정상 동작이 발생할 수 있다.

### 4-3. 대기 기능이 없어 busy-waiting이 발생함
버퍼가 비어 있을 때 소비자가 자동으로 기다리는 기능이 없다. 그래서 소비자는 계속 반복문을 돌며 CPU를 소모하게 된다.

### 4-4. 종료 신호 체계가 없음
생산이 끝났다는 사실을 소비자에게 알려주는 신호가 없기 때문에, 소비자는 언제 종료해야 할지 알 수 없다.

## 5. 결론
이번 실험을 통해 `ArrayList`를 공유 버퍼로 사용하는 방식은 생산자-소비자 문제에 적합하지 않다는 점을 확인했다.

문제점은 다음과 같았다.

- 스레드 안전하지 않음
- 메시지 유실 또는 중복 가능성 존재
- busy-waiting으로 CPU 낭비
- 종료 시점 제어 어려움

따라서 이후 단계에서는 `BlockingQueue`처럼 스레드 안전하고, 비어 있을 때 대기할 수 있는 자료구조를 사용하는 것이 적절하다.

## Step 4-2 synchronized와 BlockingQueue 비교 실험 보고서

### 1. 실험 목적
Step 4-1에서 확인한 `ArrayList` 기반 공유 버퍼의 문제를 두 가지 방식으로 개선하였다.

- 단계 A: `synchronized`, `wait()`, `notify()`를 사용하여 직접 동기화
- 단계 B: `LinkedBlockingQueue`로 대체하여 동시성 제어를 단순화

이를 통해 예외 발생 여부, CPU 사용률, 종료 처리 방식, 코드 복잡도를 비교하였다.

### 2. 단계 A - synchronized 적용

#### 2-1. 적용 내용
`ArrayList<String>`를 그대로 유지하면서, 생산자와 소비자의 버퍼 접근을 `synchronized(buffer)`로 보호하였다.

- 생산자
  - `buffer.add()`를 `synchronized(buffer)` 블록 안에서 수행
  - 메시지 추가 후 `buffer.notify()` 호출
- 소비자
  - `synchronized(buffer)` 블록 안에서 버퍼가 비어 있으면 `buffer.wait()`로 대기
  - 버퍼에 데이터가 있으면 `buffer.remove(0)`으로 꺼내기
- 종료 처리
  - 생산자가 마지막에 `"END"`를 버퍼에 추가
  - 소비자는 `"END"`를 받으면 종료

#### 2-2. 관찰 결과
이 방식에서는 Step 4-1에서 보였던 busy-waiting이 사라졌다. 소비자는 버퍼가 비어 있을 때 계속 반복문을 돌지 않고 `wait()` 상태로 대기하므로 CPU 점유율이 눈에 띄게 줄었다.


또한 생산자와 소비자의 버퍼 접근이 동기화되어, `ArrayList`를 직접 사용할 때 발생할 수 있었던 경쟁 조건과 예외 가능성이 크게 줄어들었다.

다만 코드가 복잡해졌다. 락 획득, 대기, 깨우기, 종료 신호 처리까지 모두 직접 관리해야 했기 때문이다.

### 3. 단계 B - BlockingQueue 대체

#### 3-1. 적용 내용
단계 A의 공유 버퍼를 `LinkedBlockingQueue<String>`로 교체하였다.

- 생산자
  - `queue.put(message)`로 메시지 추가
- 소비자
  - `queue.take()`로 메시지 꺼내기
- 종료 처리
  - 생산자가 마지막에 `"END"`를 `put()`
  - 소비자는 `"END"`를 `take()`하면 종료

이 과정에서 다음 요소들이 모두 사라졌다.

- `synchronized`
- `wait()`
- `notify()`

#### 3-2. 관찰 결과
`BlockingQueue`는 내부적으로 스레드 안전성과 대기 메커니즘을 제공하므로, 생산자와 소비자가 같은 큐를 사용해도 별도의 동기화 코드를 작성할 필요가 없었다.

- 큐가 비어 있으면 `take()`가 자동으로 대기
- 큐에 데이터가 들어오면 소비자가 자동으로 이어서 처리
- 필요 시 생산자도 `put()`에서 자연스럽게 대기 가능

즉, 단계 A와 동일한 동작을 더 짧고 단순한 코드로 구현할 수 있었다.

### 4. put()/take()만으로 동일한 동작이 되는 이유
`LinkedBlockingQueue`는 내부적으로 동기화와 대기/깨우기 기능을 이미 구현하고 있다.

- `put()`
  - 데이터를 안전하게 큐에 넣는다
  - 큐가 가득 차면 자동으로 대기한다
- `take()`
  - 큐에서 데이터를 안전하게 꺼낸다
  - 큐가 비어 있으면 데이터가 들어올 때까지 자동으로 대기한다

따라서 개발자가 직접 `synchronized`, `wait()`, `notify()`를 작성하지 않아도 생산자-소비자 구조가 올바르게 동작한다.

### 5. 세 가지 방식 비교

| 구분 | ArrayList 방식 | synchronized 방식 | BlockingQueue 방식 |
|---|---|---|---|
| 코드 라인 수 | 가장 적어 보이지만 문제 해결 코드가 없음 | 가장 많음 | 비교적 적음 |
| 스레드 안전성 | 없음 | 있음 | 있음 |
| 대기 방식 | 없음, busy-waiting 발생 | `wait()` / `notify()` 직접 사용 | `put()` / `take()`가 자동 처리 |
| 예외/경쟁 조건 위험 | 높음 | 낮아짐 | 낮음 |
| 종료 처리 | 어려움 | `"END"` 신호로 가능 | `"END"` 신호로 가능 |
| CPU 사용률 | 높음 | 낮음 | 낮음 |
| 구현 난이도 | 쉬워 보이지만 불완전 | 복잡함 | 가장 단순함 |

### 6. 결론
세 가지 방식을 비교한 결과, `ArrayList`를 공유 버퍼로 사용하는 방식은 동시성 문제를 해결하지 못하고 busy-waiting까지 발생하여 적합하지 않았다.

`synchronized`와 `wait()/notify()`를 적용하면 문제를 해결할 수는 있었지만, 코드가 길어지고 직접 관리해야 할 요소가 많아졌다.

반면 `BlockingQueue`는 동일한 생산자-소비자 구조를 더 간단하고 안전하게 구현할 수 있었다. 따라서 동시성 기반 메시지 전달 구조에서는 `BlockingQueue`가 가장 적절한 선택이라고 판단했다.
# 4-6 과제 4-5에서 생산 속도와 소비 속도를 다르게 설정해보라.
- 생산 속도가 소비 속도보다 빠르면 버퍼에 메시지가 누적된다.
- 소비 속도가 생산 속도보다 빠르면 소비자는 `poll()`에서 대기한다.
- `BlockingQueue`를 사용하면 생산자와 소비자의 속도가 달라도 자연스럽게 조절된다.
- 이 과정에서 busy-waiting 없이 안전하게 동작한다.
