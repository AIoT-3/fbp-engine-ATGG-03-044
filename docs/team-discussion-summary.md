# 팀 토의 정리

## 1. ProtocolNode / 외부 통신 노드 공통 설계

### 1-1. 프로토콜 노드의 연결 실패를 엔진에 어떻게 알릴 것인가?
- 현재 FBP 구조에서는 에러 전용 `OutputPort`로 전달하는 방식이 가장 자연스럽다.
- 이유:
  - 기존 메시지 흐름과 같은 방식으로 다룰 수 있다.
  - 다음 노드에서 에러 로깅, 알림, 분기 처리를 할 수 있다.
- 대안으로 이벤트 버스 방식도 가능하지만, 지금 구조에서는 오히려 개념이 하나 더 늘어난다.

### 1-2. 재연결 시 기존 플로우의 다른 노드는 어떻게 동작해야 하는가?
- 가능한 선택:
  - 대기
  - 메시지 버림
  - 큐에 저장
- 현재 프로젝트 수준에서는 `버림 + 에러 알림`이 가장 단순하고 안전하다.
- 이유:
  - 무한 큐 적재는 메모리 문제를 만들 수 있다.
  - 모든 노드를 대기시키는 구조는 현재 엔진과 잘 맞지 않는다.

### 1-3. config 정보를 코드에 하드코딩하지 않고 외부에서 주입하는 방법은?
- 가장 현실적인 방법은 `properties` 또는 `yaml/json` 설정 파일 사용이다.
- 현재 프로젝트는 아직 외부 설정 파일까지 요구하지 않았지만, 이후 확장 시 가장 먼저 적용할 수 있는 지점이다.
- 지금은 `Map<String, Object>` 기반 config를 쓰고 있으므로, 외부 설정을 읽어 이 `Map`으로 넘기는 구조로 자연스럽게 확장 가능하다.

## 2. MQTT 관련 토의

### 2-1. MqttSubscriberNode와 MqttPublisherNode가 같은 Broker를 사용할 때, client ID 충돌을 어떻게 방지하는가?
- 같은 Broker에서는 client ID가 중복되면 안 된다.
- 같은 ID로 접속하면 한 쪽 연결이 강제로 끊길 수 있다.
- 권장 방식:
  - 역할 기반 이름 부여
    - 예: `mqtt-subscriber-1`, `mqtt-publisher-1`
  - 필요하면 UUID suffix 추가
- 원칙:
  - client ID는 Broker 전체에서 고유해야 한다.

### 2-2. 여러 토픽을 구독해야 할 때, 노드 하나로 처리할 것인가 토픽마다 노드를 만들 것인가?
- 노드 하나로 여러 토픽 처리
  - 장점: 연결 수 감소, 관리 대상 감소
  - 단점: 내부 분기 로직이 복잡해짐
- 토픽마다 노드 분리
  - 장점: 책임 분리 명확, 테스트 쉬움, 플로우 가독성 좋음
  - 단점: 연결 수 증가
- 현재 프로젝트 수준에서는 토픽 의미가 다르면 나누는 쪽이 더 단순하고 안전하다.

### 2-3. QoS 레벨은 상황에 따라 어떻게 선택해야 하는가?
- QoS 0
  - 빠름
  - 유실 가능
  - 일반 센서 텔레메트리, 주기 데이터
- QoS 1
  - 최소 한 번 전달
  - 중복 가능
  - 경고, 상태 변화, 중요한 이벤트
- QoS 2
  - 정확히 한 번
  - 가장 무겁고 느림
  - 꼭 필요한 경우만
- 현재 구조에서는 기본값 `QoS 1`이 가장 현실적이다.

### 2-4. 연결이 끊겼다 재연결될 때, 구독은 자동으로 복원되는가?
- 자동 재연결과 자동 재구독은 같은 문제가 아니다.
- 현재 코드에서 `automaticReconnect = true`는 재연결 시도를 의미할 뿐이다.
- 재연결 후 구독 복원은 명시적으로 재구독 로직을 넣는 편이 안전하다.
- 현재 구현에서는 `MqttSubscriberNode`의 `connectComplete()`에서 재구독을 수행하도록 보완했다.

### 2-5. MQTT 쪽에서 실제로 어떤 문제가 있었고, 어떻게 해결했는가?

#### 실제로 확인한 문제 1: `subscribe(..., listener)` 경로에서 `StackOverflowError`
- 우리가 실제로 밟은 문제는 `MqttClient.subscribe(String topic, int qos, listener)` 사용 시 발생한 `StackOverflowError`였다.
- 이 문제는 단순한 “메시지 버퍼 overflow”가 아니라, **호출 경로 자체에서 재귀가 발생하는 형태의 stack overflow**였다.
- 즉, 우리가 실제로 겪은 에러는 **`StackOverflowError`** 였다.

#### 해결 방식 1: 콜백 등록과 구독 분리
- 문제 경로:
  - `subscribe(topic, qos, listener)`
- 우회 방식:
  - `setCallback(...)`
  - `subscribe(topic, qos)`
- 이유:
  - 같은 라이브러리 안에서 실제로 정상 동작하는 경로가 확인되었기 때문이다.

#### 실제로 확인한 문제 2: file persistence 부산물 생성
- 기본 `MqttClient` / `MqttAsyncClient` 생성자를 그대로 쓰면 client ID 이름으로 디렉토리와 `.lck` 파일이 생성되었다.
- 예:
  - `mqtt-publisher-connect-.../.lck`
  - `mqtt-test-pub-.../.lck`
- 원인:
  - Paho 기본 file persistence 사용

#### 해결 방식 2: `MemoryPersistence` 사용
- 생성자를 다음처럼 변경했다.

```java
new MqttAsyncClient(brokerUrl, clientId, new MemoryPersistence())
```

- 결과:
  - `.lck`
  - `mqtt-*` 디렉토리
  - file persistence 부산물
  가 생기지 않게 되었다.

#### 최종 선택
- 단순 반복 연결/종료 테스트에서 `MqttClient` 자체가 무조건 실패하는 것은 확인되지 않았다.
- 하지만:
  - 실제로 `subscribe(..., listener)` 경로에서 `StackOverflowError`를 밟았고
  - file persistence 부산물이 불편했고
  - 현재 과제에서는 보수적 안정성이 더 중요했기 때문에
- 최종적으로는 `MqttAsyncClient + MemoryPersistence`를 선택했다.

## 3. MODBUS 관련 토의

### 3-1. MODBUS 폴링 주기를 어떻게 결정해야 하는가?
- 고려 요소:
  - 장비 응답 속도
  - 네트워크 지연
  - 장비 부하
  - 필요한 데이터 신선도
- 주기가 너무 짧으면:
  - 장비 부하 증가
  - 타임아웃/충돌 가능성 증가
- 주기가 너무 길면:
  - 데이터 지연
  - 제어 반응성 저하
- 현재 프로젝트에서는 `1초` 수준이 데모/테스트에 가장 무난하다.

### 3-2. 레지스터 값의 스케일 변환을 노드 안에서 할 것인가, 별도 TransformNode에서 할 것인가?
- 노드 안에서 처리
  - 장점: 바로 의미 있는 값으로 변환 가능
  - 단점: 프로토콜 노드 책임이 커짐
- 별도 `TransformNode`에서 처리
  - 장점: 책임 분리 명확, 재사용 쉬움
  - 단점: 플로우가 길어짐
- 현재 구현은 `registerMapping`이 있으면 `ModbusReaderNode`에서 변환 가능하게 했고, 필요하면 이후 `TransformNode`로도 분리할 수 있는 구조다.

### 3-3. MODBUS 통신 에러(타임아웃, 응답 없음) 시 어떻게 처리해야 하는가?
- Reader 쪽:
  - 예외를 그대로 죽이지 않고 `error` 포트로 전달하는 방식이 적절하다.
- Writer 쪽:
  - 현재는 로그 출력으로 처리
  - 필요하면 `result/error` 분리도 가능
- 즉, 외부 통신 에러는 FBP 메시지 흐름 안에서 다루는 것이 현재 구조와 가장 잘 맞는다.

### 3-4. 여러 레지스터를 읽을 때, 하나의 요청으로 묶어 읽는 것과 개별 요청의 장단점은?
- 하나의 요청으로 묶기
  - 장점: 네트워크 왕복 감소, 성능 효율적
  - 단점: 일부 값만 필요해도 같이 읽게 됨
- 개별 요청
  - 장점: 필요한 값만 읽을 수 있음
  - 단점: 요청 수 증가, 지연 증가
- 현재는 **가능하면 묶어서 읽고**, 이후 필요 시 `registerMapping`으로 의미를 분리하는 쪽이 현실적이다.

### 3-5. 소켓을 매 요청마다 열고 닫을 것인가, 연결을 유지할 것인가?
- 매 요청마다 연결
  - 장점: 구현 단순, 상태 꼬임 적음
  - 단점: 성능 비효율, 연결 오버헤드 큼
- 연결 유지
  - 장점: 성능 좋음, 폴링 구조에 유리
  - 단점: 끊김/재연결 처리 필요
- 현재 구조는 `ProtocolNode` 생명주기에 맞춰 연결 유지 방식이 더 적합하다.

### 3-6. Transaction ID를 관리하는 이유는 무엇인가?
- MODBUS TCP에서 요청과 응답 쌍을 식별하기 위해 필요하다.
- 요청마다 증가시키고, 응답의 Transaction ID와 비교하면
  - 지금 받은 응답이 내가 보낸 요청에 대한 것인지 확인할 수 있다.
- 생략하면:
  - 응답이 섞였을 때 구분이 어려워진다.
  - 잘못된 응답을 정상 응답으로 오해할 수 있다.

## 4. 현재 결론
- ProtocolNode 계열은 에러 포트와 외부 config 확장 방향으로 가는 것이 적절하다.
- MQTT는 현재 `MqttAsyncClient + MemoryPersistence`가 가장 보수적이고 깔끔한 선택이다.
- MODBUS는 시뮬레이터 기반으로 로컬 통합 테스트가 가능하므로, Step 3 기능 검증에 유리하다.

## 5. Rule / 통합 플로우 관련 토의

### 5-1. 규칙 표현 방식으로 어떤 옵션을 선택했는가? 그 이유는?
- 기본 선택은 **옵션 A: `Predicate<Message>` 기반**이 가장 적절하다.
- 이유:
  - 구현이 가장 단순하다.
  - 타입 안정성이 높다.
  - 디버깅이 쉽다.
  - 기존 테스트 스타일과 잘 맞는다.
- 확장이 필요하면 다음 단계로 `RuleExpression`을 추가하는 것이 좋다.
- 즉 현재 프로젝트 기준 권장 순서는:
  - 1차: Predicate 기반
  - 2차: 문자열 기반 확장

### 5-2. 규칙이 복잡해지면 노드 하나에 넣을 것인가, 여러 노드를 조합할 것인가?
- 단순 조건은 `RuleNode` 하나에 두는 것이 맞다.
- 하지만 규칙이 복잡해질수록 여러 노드를 조합하는 쪽이 더 안전하다.
- 이유:
  - 책임 분리
  - 테스트 단위 분리
  - 플로우 가독성 유지
- 현재 구조에서는:
  - 단일 조건 -> `RuleNode`
  - 다중 조건 결합 -> `CompositeRuleNode`
  - 시간 조건 -> `TimeWindowRuleNode`
  처럼 역할을 나누는 것이 적절하다.

### 5-3. 시간 기반 규칙에서 메시지 누락(네트워크 지연 등)은 어떻게 고려하는가?
- 가장 단순한 현재 구현 기준은 **노드가 메시지를 처리한 시각**을 기준으로 본다.
- 이 방식은 구현이 단순하지만, 네트워크 지연이 큰 경우 실제 발생 시각과 차이가 날 수 있다.
- 더 정확하게 하려면:
  - 메시지에 event timestamp를 포함하고
  - TimeWindowRuleNode가 그 값을 기준으로 평가해야 한다.
- 현재 단계에서는 처리 시각 기준으로 시작하고, 필요 시 event timestamp 기준으로 확장하는 것이 현실적이다.

### 5-4. 규칙을 외부 파일(JSON/YAML)로 정의하고 런타임에 로드하는 방법은?
- 가장 현실적인 방법은 아래 흐름이다.
  1. JSON/YAML 파일 읽기
  2. DTO 또는 `Map<String, Object>`로 변환
  3. `RuleExpression` 또는 `CompositeRuleNode` 구성
  4. 엔진 시작 시 로드
- 런타임 변경까지 지원하려면:
  - 파일 재로드
  - watcher
  - 또는 재시작 시 재적용
  같은 전략이 필요하다.
- 현재 프로젝트 수준에서는 **시작 시 한 번 로드하는 방식**이 가장 단순하고 적절하다.
